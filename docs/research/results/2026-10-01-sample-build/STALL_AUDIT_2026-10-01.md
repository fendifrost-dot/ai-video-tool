## 2. The three structural roots

**A. The scratch sandbox is doing render-farm work with no resource governor.** 8 GB, 2 cores, no swap, no GPU; the compositor keeps whole takes in RAM; the gate loads three models; both run whenever I start them, with nothing refusing the second when the first is using the memory. Every "silent stall" today was this.

**B. Batch work borrows a human's one-hour browser token.** Every edge function requires a user JWT (correct for the app), so the batch runner, the gate's judge, storage signing and uploads all stop on the hour. There is no machine identity for unattended jobs, and the token cannot be refreshed from here by policy.

**C. There is no job runner — just scripts with `nohup`.** Submits are not written ahead of the call; polls block the operator's turn or run as orphaned shells; a crash between a paid submit and its record loses the job; concurrency is "whatever I remembered not to start"; there is no pre-flight on provider balance or on the box's free memory.

## 3. What to change, in order of leverage (all general, none project-specific)

1. **Compositor memory budget** (`composite_environment.py`): stream alphas and decontaminated foregrounds to disk (the `fgr_dir` path already exists — make it the only path), compute the temporal median in a sliding window of `--temporal` frames instead of a second full-clip array, build the background prior from uint8 frames with a running nan-median over chunks, free the segmenter masks after the hard matte. Target: < 1.5 GB for a 7 s 1080p take, so a composite and the gate can share the box. Expected effect: no OOM, and two composites in parallel on a 2-core box is still CPU-bound, so wall-clock per take stays ≈ 8–10 min until there is a worker (item 5).
2. **A resource governor for local jobs** (new `scripts/_lib/jobs.py`, used by every runner): a lock file with a memory reservation per job class (composite 2 GB, gate 2.5 GB, batch 0.3 GB); a job refuses to start when `MemAvailable` minus reservations is below its need and queues instead; every runner registers a PID file so stopping a job is by id, never by `pkill -f`. One module, every script calls `with job("composite", need_gb=2.0):`.
3. **Write-ahead manifest + crash-safe submits** (`run_world_batch.py`, `run_broll_batch.py`): write the shot's `submitting` record with the request body before the API call, then the envelope after; on resume, any `submitting` without a job id is reconciled against Control Center's `tool_execution_logs` (what I did by hand today) before anything is resubmitted. Pre-flight before a batch: provider balance where an API exposes it (Runway does; Higgsfield's dashboard does not), the prompt cap per provider from capability data, and a dry-run estimate against the ledger ceiling.
4. **A batch identity instead of the browser token.** Proposal, for Fendi to approve because it touches auth: a dedicated `batch-token-proxy` edge function that mints a short-lived Supabase session for the batch runner from a server-held refresh token for his own account, callable only with a secret the runner holds (`AVT_BATCH_SECRET`), rate-limited, logged, and revocable by rotating the secret. It widens nothing on the existing proxies — they keep requiring a user JWT; it only removes the hourly hand-copy. The alternative that widens nothing at all is to run the runner inside the app (a "Batch" page that holds the live session and calls the same scripts' logic via edge functions) — the product shape, but a bigger build. Until one exists, every unattended run is bounded by the hour.
5. **The render worker** (already on the roadmap): compositing, matting and the camera engine belong on a GPU box with a queue (the shot spec is already data). On a single T4-class GPU RVM runs ≈ 25× faster than here; the 80-minute sample becomes ≈ 4 minutes. This is the fix for #2 and the reason #1 should not be over-engineered: the budget work in item 1 is what keeps the sandbox usable in the meantime, not the end state.
6. **Asynchronous shape everywhere**: any provider call that can exceed 120 s is submit-and-poll (the Higgsfield/Runway/Grok B-roll functions are; the visualiser is per-line parallel; `grok-video-edit-proxy` and `world-still-proxy` are synchronous and sit under the gateway's cap only because their providers answer in < 90 s — they should gain a background-task mode before any model that answers slower is added).

## 4. What I will not do

Raise the gateway timeouts (not ours to raise), run two compositors at once on this box (CPU-bound either way), or widen auth on any existing proxy (hard lock). Item 4 is a proposal, not a change.
